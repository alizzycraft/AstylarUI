# Semantic Application Behavior and Accessibility Parity — Phase 10

Phase 10 adds a browser-integrated semantic counterpart to Astylar's Babylon-rendered interface. Babylon remains the only visual renderer. The semantic bridge derives native, visually clipped elements from the same serializable `SiteData`, maintains them with the scene lifecycle, and routes future semantic input into the existing typed interaction system rather than creating a second application implementation.

## Acceptance gates

- Chromium accessibility snapshots for every requested authored ID match the equivalent HTML reference exactly.
- Authored hierarchy, roles, accessible names/descriptions, values, states, focus, activation, navigation, dialog modality, table relationships, and status updates are compared only where the harness observes them.
- Stable, unique authored IDs retain semantic-node identity across compatible updates; removal, incompatible replacement, and disposal release owned nodes and registrations.
- Babylon implementation meshes are not exposed as semantic nodes, and the semantic tree is not a visual renderer.
- Existing screenshot, geometry, text, interaction, lifecycle, build, and full-corpus thresholds do not regress.

## Supported public Phase 10 boundary so far

- Browser semantics are enabled by default for `Astylar.render()`. Consumers may pass `accessibility: false` or provide `accessibility: { host }` when the semantic root must live in a specific DOM container.
- The Babylon canvas is marked `aria-hidden="true"` while its semantic bridge is active, preventing its implementation surface from duplicating authored content. Its previous `aria-hidden` value is restored during disposal.
- The bridge creates a visually clipped native subtree and mirrors the authored `SiteData` hierarchy for supported native element types. It does not reproduce visual layout or paint.
- Native semantic IDs are instance-prefixed to avoid collisions between a page, multiple scenes, and surrounding application DOM. The original ID is retained as `data-astylar-id` for deterministic inspection.
- A unique authored ID is the compatibility key for native semantic-node identity. Unkeyed or duplicate-ID elements use deterministic structural paths; removed and hidden elements are removed from the semantic subtree.
- The supported structure includes headings; header, footer, navigation, main, section, article, and complementary landmarks; paragraphs; lists; anchors; buttons; forms and labels; and native table structure. Explicit accessible naming, the control-state subset described below, and semantic focus/activation are supported.
- Accessible names follow Chromium's supported browser precedence: valid `aria-labelledby`, `aria-label`, native label/alt semantics, then supported element text. `aria-describedby` remains a separate description source. Authored ID references are rewritten into the bridge instance's collision-safe native namespace and update with the semantic tree.
- Missing or removed ID references are retained as safe unresolved native references and Chromium applies its normal fallback. Repeated reference tokens retain browser behavior rather than being silently normalized by Astylar.
- Text inputs, textareas, checkboxes, radios, buttons, and single-selects expose their supported native types, values, disabled/required/readonly state, and browser-derived validity. Serializable select option arrays become native option children with disabled and selected state.
- Scene-owned mutable control state is synchronized into the native subtree after public event dispatch and its associated default action have settled. One coalesced all-control pass preserves radio-group and form-reset atomicity; compatible update/reflow also synchronizes after restoring live state.
- Native semantic focus, Tab/Shift+Tab, keyboard activation, and click activation route into the existing scene interaction runtime. Scene pointer and keyboard focus is reflected back to the semantic subtree after stable action boundaries; pointer-selection transactions and compatible reflow retain text selection, caret, scroll, and browser-compatible event order.
- Anchors with `href` participate in the shared focus and activation path. Accepted same-document fragments scroll their destination through scene-owned scroll containers; accepted external URLs emit a typed navigation outcome to an optional host callback. Canceling the typed `click` prevents either default.
- Astylar records external navigation as an intent instead of changing `window.location`. Hosts retain ownership of routing, new-window policy, and application-specific navigation side effects.
- A `dialog` with `open: true` and `modal: true` participates in the supported modal subset. The last active modal owns the interaction top layer; autofocus (or the first focusable descendant) receives initial focus, Tab/Shift+Tab wraps within its focus order, background semantic content becomes inert, and background canvas input is suppressed.
- Escape dispatches typed `keydown` followed by a cancelable, non-bubbling `cancel` on the active dialog. If accepted, Astylar closes its live presentation, restores a still-valid pre-open invoker, routes keyup to the restored target, and emits non-bubbling `close` after keyup. Application handlers remain outside serializable `SiteData` and may call `preventDefault()` on `cancel` to keep the dialog open.
- Removing an active modal with `Astylar.update()` clears focus, top-layer, picking, and semantic inertness without synthesizing `close` or restoring the invoker, matching the measured Chromium DOM-removal boundary. Reasserting an authored open modal in a later update opens a fresh live presentation.
- Modal behavior does not synthesize visual dialog chrome or a backdrop. Authors retain normal Astylar style control over dialog paint and may explicitly author any backdrop treatment their application needs.
- The implementation canvas is programmatically focusable for its scene input path but removed from sequential Tab order while the semantic bridge is connected. Its previous tabindex is restored during disposal, and delegated semantic listeners are removed.
- Interaction fixtures with `semanticIds` capture Chromium accessibility nodes after every action group and compare HTML to Astylar exactly. This covers live semantics without treating the hidden native controls as a second application state owner.
- The parity harness requests browser accessibility snapshots only for explicit `semanticIds`. It compares the browser-produced hierarchy plus Chromium's computed role, name, description, value, URL, and supported properties exactly and does not infer or claim screen-reader speech.
- Semantic node, event-registration, and observer-registration ownership are present in runtime diagnostics and semantic nodes reach zero after scene disposal.

## Intentional exclusions at this point

Phase 10 is still in progress. Status and validation announcements, representative application semantic workflows, and repeated semantic/modal lifecycle stress remain to be implemented and verified. Concurrent stacked/nested modal queues are outside the current single-active-modal subset. The final Phase 10 exclusions remain exact speech across browser/screen-reader combinations, complex ARIA widgets, `contenteditable`, multi-select, drag-and-drop, IME composition, full mobile virtual-keyboard behavior, exhaustive native validation wording, a complete application router, and advanced CSS animations/transitions.
